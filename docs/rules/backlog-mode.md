## Backlog Mode

Applies when the user says to work on the backlog (unless [prototyping-mode.md](prototyping-mode.md) is on, which replaces its branch and PR rules). It adds an autonomous, branch-per-task workflow on top of [backlog.md](backlog.md); where the two overlap, backlog.md's rules on task files still hold.

Don't stop to ask which task to take or to confirm scope. Work through the tasks in `docs/backlog/` one at a time, highest priority first (`p0` before `p1`, and so on), skipping tasks whose `depends_on` files are still in `docs/backlog/`. Before starting each task, check for `docs/backlog/.stop`; if it exists (the user creates it with `touch`), finish and commit the current task, then stop:

- **One branch per task, with a prefix.** Start each task from a fresh, up-to-date `origin/main` (fetch first) on a branch named `backlog/<task-filename-without-extension>`. Never stack one task's branch on another's (if a task truly depends on another, say so in its `depends_on` and leave it for after that merges), and never commit backlog work to `main`.
- **Finish what you can.** Implement the task, add tests, update `docs/features/` and remove the task file in the same branch (see Completing Work in backlog.md), commit with a `git log`-style message, and push (`git push -u origin <branch>`). Pushing a `backlog/*` branch is pre-authorized in this mode and doesn't deploy. Before every commit, and before moving on to the next task, run every check that can run in the environment: the full test suites (backend and web), linters, type checks, the build, and any migration or browser check the task touches. Fix failures before committing; never commit or move on with a known failure. If a check can't run here (no Docker, no `node_modules`, no network), try the nearest substitute that does (for example a syntax check), then say plainly in the commit message and your report which checks you couldn't run and what is therefore unverified. Unverified work is not a reason to stop: record what is needed to verify it (the missing tool, machine or account, and the exact commands to run) in that task's own file on its branch, under an `Unverified` section with `branch:` frontmatter, push the branch, and continue to the next backlog item.
- **On a blocker, push and note it.** If you hit something only the user can decide or do (a product or privacy call, a risky migration, new infrastructure, an account or secret), commit the work so far and push the branch. Record what's done and what's blocking in that task's own file on the same branch (a `Blocked` section, plus `branch:` frontmatter). Don't edit other tasks' files or any shared index. Then move to the next task.
- **Deliberately not building something is a valid outcome.** Keep the task file and write *why* in it (a migration risk, a product or privacy decision only the user can make, or a new-infrastructure call that "no new infrastructure without asking" in [conventions.md](conventions.md) covers), so the next session skips it on purpose instead of re-discovering the blocker.
- **Build the conservative version.** When a call is genuinely the user's, build the cautious option behind the blocker note rather than guessing silently, and document the choice in the feature doc.
- **Keep going until the user says to stop.** Backlog mode is a loop, not a single pass. After each task, immediately pick the next one and start it; don't pause to report, summarize, or ask whether to continue. Only the user ending the session ends the loop. If every remaining task looks blocked or done, don't exit: re-fetch `origin/main` and the branch list (merges may have unblocked tasks), re-read each skipped task to see whether a conservative version can be built (see "Build the conservative version"), and use `docs/backlog/` follow-ups and the "Verify before trusting" checks below to find more work. Missing local tooling (no tests, no Docker, no network) is not a reason to stop: build what you can, commit it, and say plainly in the commit message and report which checks you couldn't run. Don't pause, announce, or ask before moving on to the next task: the user wants it done without a prompt, so finish one and start the next in the same turn. Don't send a status message between tasks; the only report is the full per-branch one (complete, partial with blocker, or untested), given when the user asks for it or ends the session.
- **Pull requests.** Pull request tooling may not be authenticated on every machine, so don't count on opening PRs from a session. Every pushed `backlog/*` branch must still end up with a PR: use the project's PR-opening command (see its docs) on a machine that is logged in to the right account, and write each branch's last commit message as the PR description. List every branch you pushed in your report so none are missed. If the project automates this (a CI workflow or make target that opens a PR per `backlog/*` branch), its docs say so.
- **Never merge or push to `main`, and never deploy.** The user reviews and merges.

### Verify before trusting

Backlog and feature docs drift like any other doc. A "still unbuilt" note has turned out to be stale more than once because the fix had already shipped, and a checkmark can be wrong the other way. Check the code before believing either direction, and before deleting a task as already built.
